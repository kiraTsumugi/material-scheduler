# 05 · 复盘

## 最难的问题

**1. 区分"保存成功"与"可发布"，是本题的语义陷阱。**
最初把冲突消解后的结果也标成 `draft_saved`，看似完成了任务，实则掩盖了"待用户确认"这一关键状态。
题目特意强调"不得称为已发布""标记待确认"，本质是在考**状态模型的设计**——一个状态字段扛不住
"已保存/待确认/被阻断/失败"四种正交语义。拆成独立状态码后才自洽。教训：状态设计错了，
后面所有逻辑都在给这个错误打补丁。

**2. 让 Mock "真"地驱动决策，而不是走剧本。**
最省事的做法是 Mock 里写死 `if 冲突: 改时段`。但那样两条路径其实是同一段 if，不算 ReAct。
最终方案是让 Mock 从对话历史里**还原工具返回的事实**再决策 —— 决策分支真正由工具输出驱动，
换一个素材/时段就会走出不同的动作序列。这是"工具产出事实、模型消费事实"的正确姿势。

**3. 幂等键的选择。**
从"跑一遍看看有没有重复"（O(n) 扫描、易漏）改为"以 (素材,请求时段) 哈希为字典键"（O(1)、天然幂等）。
数据结构选对了，重复提交问题自动消失——不需要额外代码。

## 学习收获

- **好品味 = 消除特殊情况**：把"缺失/违规""保存成功/可发布"这些看似要写 if 的分支，
  下沉到数据结构与状态设计里，代码主干就干净了。
- **框架不是答案**：这题用框架（LangGraph 等）只是在 30 行循环外包一层，反而增加依赖与理解成本。
  能解释取舍比用不用框架重要。
- **验证要"真"**：不接受"看起来对"。live 路径必须起 server 验证 HTTP 契约，
  否则无从知道它是不是纸面代码。

## 下一步

1. **接真实模型跑一轮**：配 `MODEL_*`，对比真实 LLM 与 Mock 的决策差异，评估 prompt 的鲁棒性
   （例如模型是否会"自作主张"改 hard 要求——这是最需要防的）。
2. **持久化 + 并发安全**：把 `DraftStore` 换成带唯一索引的存储，fingerprint 直接做唯一键。
3. **多日排期**：当前单日，扩展到跨日冲突消解。
4. **规则热更新**：规则目前是静态 JSON，可加版本与生效时间。
5. **人工确认闭环**：`needs_confirm` 后接一个确认入口，确认后草稿转正式（仍不真实发布）。
